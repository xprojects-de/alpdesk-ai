# The frontend's languages

The frontend speaks English and German, and more languages can be added as one file each (decided 11 October 2026,
roadmap point 27). The backend stays English: it stores a user's language
and gives its errors a code the frontend translates - it keeps no list of languages and writes no text in them.

## Decisions

1. **Translation at runtime with Transloco** (`@jsverse/transloco`), not Angular's `@angular/localize`: one jar, one
   bundle, the language switches without a reload. `@angular/localize` builds a bundle per language with its own
   `base href`, which does not fit `copyFrontend`, `SpaFallbackController`'s `<base href>` under a context path and
   `base-path.util.ts`; its runtime variant still needs a reload to switch.
2. **English is the default and the reference language.** `Frontend/src/i18n/en.json` is complete by definition; every
   other language file must have exactly its keys, no empty text and the same `{{params}}` (`i18n/i18n.spec.ts`).
   English is what an unknown browser, an unknown tag and a user from before the language column get.
3. **The language lives on the account.** `tenant_user.language` (migration V4): the admin or a tenant admin sets it
   when creating the user (default English), the user changes it in the shell's menu (`PUT /tenant/account/language`
   - **with the WAM proxy for every user of the person**: the same username in other tenants, so a switch of tenant
   keeps the language, decided 7 November 2026; **without WAM for the user's own row only** - a username proves no
   person there, the same name in another tenant may be someone else's ([tenancy.md](tenancy.md) "The switch"; fixed
   9 November 2026). **Through a WAM proxy** the frontend sends the browser's language with `POST /login/wam`:
   a user the IDM's groups create speaks it, and a waiting person's access request keeps it
   (`access_request.language`) for the admin's assignment, which takes it unless it names another - a person with a
   user already keeps its language there (`TenantUserService.languageOfPerson`); a tag of the wrong form is left out. Nobody but the user changes it later through the account; the
   admins can through the user dialog. A tenant admin's own change in either place shows at once in both: the page
   follows its own row saved in the dialog, and its row in the user list follows the menu (so the dialog never sends
   the old one back). **Before the login and for the admin** (the operator, no account row) the
   browser's language counts (decided 11 October 2026): nothing is remembered in the browser - a stored language
   would be the last person's at that screen, not the browser's. The admin may switch in the menu; that holds until
   the page is reloaded.
4. **The backend knows no languages.** It checks a tag's form only (`^[a-z]{2,3}(-[A-Za-z0-9]{2,8})*$`, at most 20
   characters, 400 otherwise - `TenantUserService.requireLanguage`) and stores it. The list of offered languages is the
   frontend's (`utils/language.util.ts`, next to the files), so a new language needs no backend change; a stored tag the
   frontend does not offer shows as the language spoken for it - "de-AT" as German, one removed since as English - in
   the list and the dialog alike, and saving the dialog stores an offered one.
5. **The chat is untouched.** The models answer in the language of the question (`ChatService`'s system prompt,
   `ConversationTitles`); the UI language is not sent to them. What a tenant enters itself (instructions, templates,
   area and document names, the connected software's tools) is data and stays in its language.

## In the frontend

- **Files**: `src/i18n/<language>.json`, nested keys `<area>.<component or topic>.<text>` (`chat.input.placeholder`,
  `documents.list.empty`, `errors.document.uploadDocument`), shared words under `common.*`, Transloco's `{{param}}`
  for values. `i18n/i18n.loader.ts` imports them as chunks of their own (`import("../../i18n/en.json")`): loaded on
  demand, cached by their hashed names, served under a context path like the rest of the build - no path of their own
  for the reverse proxy or the smoke test.
- **Start**: an app initializer picks the language before anything is shown - the browser's first offered language
  (`navigator.languages`), else English (`browserLanguage`) - and waits for its file, so no key flashes. `LOCALE_ID`
  (only for what Angular formats itself) is fixed from it.
- **The `language` slice** holds the spoken language. `useLanguage` (start, after a logout - the browser's again -,
  the account loaded - the account wins over the browser) and `chooseLanguage` (the shell's menu - saved to the tenant
  user's account; a failed save keeps the language and says so) both switch Transloco and `<html lang>`
  (`LanguageEffects`). Nothing of it is stored in the browser.
- **Templates**: the `transloco` pipe for every text and every shown attribute (`[attr.aria-label]`, `[matTooltip]`,
  `[placeholder]`, inputs of `app-page-header` / `app-empty-state`); dates and numbers through transloco-locale's
  `translocoDate` / `translocoDecimal` (en → en-GB: day before month, 24 hours; de → de-DE), which follow a switch at
  once. Plurals are two keys (`.one` / `.other`) chosen in the template - no ICU plugin.
- **Code**: a snackbar's or dialog's text is translated at the moment of the event (`TranslocoService.translate`),
  never in a field initializer. Utils return keys (and params), the template translates - so they and their specs stay
  free of Transloco. Code that formats numbers or dates takes the locale from `i18n/locale.ts` (`injectLocale()`, a
  signal - a computed value is written again on a switch). Sorting and search use the browser's locale
  (`Intl.Collator(undefined, …)`).
- **Errors**: effects write their failure messages through `i18n/error-messages.service.ts` (`ErrorMessages.of(error,
  fallbackKey)`) when the failure happens - state keeps a plain string. The paginator's labels come from
  `i18n/paginator-intl.ts`.
- **Params are written in once** (`i18n/single-pass-transpiler.ts`): Transloco's own transpiler searches the text
  again after every replacement, so a name someone typed with `{{...}}` in it lost its braces - or, holding its own
  placeholder, froze the tab. Values from users and other systems (area, chat and file names, error texts) are params
  all the time.
- **Missing keys** show as the key (no silent fallback to English) - the spec keeps every language complete.
- **Lint**: `@angular-eslint/template/i18n` refuses static text with letters in a template (`eslint.config.js`):
  every visible word comes from a key. Icons (`<mat-icon>`), `<code>`/`<pre>` and attributes that are not shown
  (`ignoreAttributes` in `eslint.config.js`) are left out of the check. Its message asks for Angular's `i18n`
  attribute - never add one: it would only silence the rule; the text belongs in a key.
- **Specs** that render texts import `i18n/i18n.testing.ts` (`translocoTesting("de")`): the real files, loaded at
  once.

## Adding a language

1. `Frontend/src/i18n/<tag>.json` with every key of `en.json` (copy it, translate the texts, keep the `{{params}}`).
2. An entry in `LANGUAGES` (`utils/language.util.ts`: its tag, its own name, its locale), a line in `TRANSLATIONS`
   (`i18n/i18n.loader.ts`) and in the spec's `FILES` (`i18n/i18n.spec.ts`), and its Angular locale data in
   `app.config.ts` (`registerLocaleData`).
3. `npm test` - the spec names every key that is missing or empty. Nothing in the backend changes.

## Error codes

Every error answer the backend writes itself is an `ErrorResponse` with three fields: `message` (the English text, as
before), `code` (a stable identifier) and `params` (the values put into the message, by name, never null). The chat
stream's `error` event carries the same three fields. Two kinds of answers have no body of ours, as before: a 404 for an
unknown id that a controller answers with `HttpResponse.notFound()` (no body at all), and what Micronaut refuses
itself before a route is reached (405, 415 - its own JSON, without `code`). The frontend falls back to the action's own
text for them.

- **Naming**: exactly two lowerCamelCase segments, `<area>.<rule>` - `user.usernameTaken`, `document.typeNotSupported`.
  The area names the domain, the rule the rule, never the HTTP status. The same rule of one area shares one code
  wherever it is thrown (`tenant.notFound`); a different message gets a different code. The same wording in two areas
  keeps a code per area (`apiKey.nameRequired`, `user.nameRequired`) - a client switching on `code` learns which.
- **In the backend**: `ServiceException`'s factories take the code first and it is mandatory, so the compiler finds
  every throw site; a value the message names is a param too (`username`, `min`, `maxMb`, ...).
  `GlobalExceptionHandler` copies code and params into the body and has its own codes (`db.*`, `request.*`, `auth.*`,
  `error.unexpected`). `ErrorCodeSpec` checks the form of every code in the sources - thrown ones and the answers built
  directly (`ErrorResponse.of`, `new ErrorResponse`); `GlobalExceptionHandlerSpec` the handler's codes and params.
- **In the frontend**: `errors.backend.<code>` in every language file, with the same `{{params}}` - `en.json` holds the
  backend's message. `ErrorMessages` shows the translation, else the English `message`, else the action's fallback
  key, so a code the frontend does not know yet still shows the backend's text. No build step compares the Java codes
  with the language files (not built on purpose - a review checks a new `ServiceException`).
- **For the client software** (`/api/v1`) `message` stays English; it may switch on `code`, which is documented in
  Swagger and does not change when the wording does.
- **Not coded** (texts inside other answers, shown as they are, English): a ZIP import's skip reason per file, a
  connected software's load error, a failed document's stored `error`, and tool results (for the model). The codes of
  the tools' refusals (`tool.*`, `mcp.templateUnknown`) exist only because a `ServiceException` needs one: the
  `Toolbox` and the MCP server pass on the message alone.
